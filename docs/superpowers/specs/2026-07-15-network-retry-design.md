# Telegram 网络异常恢复设计

## 项目背景

当前机器人使用 `python-telegram-bot` 的轮询模式接收消息，并通过 HTTP/SOCKS5 代理访问 Telegram。旧实现把进入全局错误处理器的网络异常永久累计，达到 `MAX_RETRIES` 后调用 `stop_running()`。成功请求不会进入错误处理器，因此计数无法在网络恢复后清零；配合 Docker 的 `restart: always`，长期外部网络故障可能造成容器反复重启。

## 功能需求

- Telegram、代理超时等可恢复网络异常不得主动停止应用。
- 网络异常按 5 分钟静默窗口分组：距离上次网络异常超过 300 秒时，新异常从第 1 次重新计数。
- 计数仅用于诊断日志，不作为退出条件。
- 5 分钟窗口可通过 `NETWORK_ERROR_RESET_SECONDS` 调整，默认值为 `300`。
- 非网络异常继续记录完整错误信息，不改变现有业务处理流程。

## 技术约束

- 保持 `main.py` 单文件主业务结构，不引入独立调度器或额外后台任务。
- 使用 `time.monotonic()` 计算时间间隔，避免系统时间校准影响窗口判断。
- 不修改 Docker 的 `restart: always`；通过区分可恢复错误和致命错误避免重启风暴。
- 保留 `python-telegram-bot` 自带的轮询重连和退避机制。

## 实现细节

1. 删除 `MAX_RETRIES`、`MAX_NETWORK_RETRIES` 及其停止应用逻辑。
2. 新增 `NETWORK_ERROR_RESET_SECONDS` 配置，并对非法值执行启动时校验。
3. 新增网络异常状态更新函数，集中处理计数与时间窗口，便于独立测试。
4. 全局错误处理器遇到网络异常时输出本轮计数和重置窗口，然后直接返回。
5. 为窗口内累加、窗口外重置、边界值和错误类型识别补充单元测试。

## 验收标准

- 同一 5 分钟窗口内的网络错误计数递增。
- 超过 5 分钟后再次发生错误时计数从 1 开始。
- 网络错误不会调用 `application.stop_running()`。
- 非网络错误仍被记录。
- Python 语法检查和单元测试全部通过。
